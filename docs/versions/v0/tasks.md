## Phase 1 — Spine (M1)

Milestone acceptance (§19 M1): via `curl` alone — register a repo, create a one-step agent task, watch it finish, see the branch and diff.

**Phase 1 decisions (grill session, 2026-08-07):**

- *Delivery:* 4 grouped PRs along dependency seams — (1) T1.1+T1.2 config+store, (2) T1.3+T1.4 daemon+API, (3) T1.5+T1.6 projects+worktrees, (4) T1.7–T1.9 adapter+run+gate. Each independently green in CI; tasks.md updated per PR.
- *Git access:* git CLI only (no go-git) — `exec` via one internal `gitx` helper (run/capture/error-mapping). git version logged at daemon start; warn (not fail) below 2.31.
- *Platform dirs:* `os.UserConfigDir()` for config; hand-rolled ~30-line data-dir resolver (`XDG_DATA_HOME`/`~/.local/share`, `%LOCALAPPDATA%`, `~/Library/Application Support/vincent/data`). `VINCENT_CONFIG_DIR` / `VINCENT_DATA_DIR` env overrides (used by tests and the T1.9 gate). No xdg dependency.
- *YAML:* `goccy/go-yaml` everywhere (strict decode now; its line/column-annotated errors are what T2.1 needs later).
- *Config bootstrap/reload:* first start writes a fully-commented `config.yaml` with §12.3 defaults. Invalid config at startup = fatal; invalid on hot-reload = keep last-good + log rejection; `listen:` changes ignored until restart (warn). fsnotify watches the config *directory* (survives rename-on-save), ~100 ms debounce.
- *SQLite:* `modernc.org/sqlite` via `database/sql`; WAL + `busy_timeout` via DSN pragmas; `MaxOpenConns(1)` (single connection — zero SQLITE_BUSY surface; revisit only if profiling demands).
- *Migrations:* hand-rolled embedded runner — `embed.FS` of `NNNN_name.sql`, applied in-transaction at startup into the spec §14 `schema_migrations` table. Up-only; no library.
- *Store:* hand-written repository-style `database/sql` code (no sqlc/ORM); queries as consts beside their methods; covered by CRUD round-trip tests.
- *Daemon lifecycle:* detached start = self-exec `vincent daemon` with platform `SysProcAttr` (DETACHED_PROCESS / setsid). Single-instance via `gofrs/flock` on `daemon.lock` (auto-releases on death). **Spec addition:** authenticated `POST /v1/daemon/stop` endpoint — `daemon stop` calls it, waits for exit, `--force` kills as fallback; same graceful path (§12.4) on all 3 OSes. `token` + `daemon.json` written atomically (temp+rename); `daemon.json` removed on graceful shutdown.
- *Token perms:* 0600 enforced + tested on POSIX; Windows relies on `%LOCALAPPDATA%` per-user ACL inheritance (documented; no DACL code in v1) — test asserts existence/location there.
- *Logging:* `slog` TextHandler everywhere (file + foreground stderr); rotation via `natefinch/lumberjack`.
- *API:* stdlib `net/http` ServeMux with Go 1.22+ method/wildcard patterns (no chi); middleware chain auth → log → recover; constant-time token compare (`crypto/subtle`); `/v1/health` exempt; CORS disabled; stable `snake_case` error codes.
- *default_branch detection:* `origin/HEAD` → local `main` → local `master` → current HEAD branch → reject registration with clear error (detached/unborn HEAD requires explicit `default_branch`).
- *Worktree slug edge:* title sanitizing to empty → branch `vincent/{id}` (no trailing dash); otherwise §5.3 rules.
- *Agent CLI location:* **spec addition** to §12.3 — `agents: { claude: { path }, codex: { path } }`; empty = `exec.LookPath`. `Detect()` reports the resolved path in `/v1/info`. Tests/gate substitute the fake via this knob (no PATH surgery).
- *Fake agent:* committed `cmd/fakeagent` main package — scenario-driven (success / error-event / nonzero-exit / hang-until-killed / big-usage) via env/flag, emits Claude-style stream-json, prompt from stdin. Always compiled by `./...`; excluded from release packaging in T4.5; grows a codex dialect for T2.9.
- *Transcripts:* agent stream-json written verbatim (lossless/replayable); vincent's own annotations as namespaced `{"type":"vincent.…"}` JSONL lines. Parsing is tolerant — unknown event types transcripted but not normalized; exact CLI flags pinned at implementation time (§9.2).
- *M1 task shape:* `workflow` param optional (default `"adhoc"`); daemon synthesizes a real one-step workflow YAML (agent step; prompt = fixed template embedding title+description) stored as `workflow_snapshot` — DB rows shape-final; T2.3 swaps synthesis for registry lookup.
- *M1 admission:* interim FIFO (`created_at`) runner bounded by global `max_parallel_tasks`; priority ignored until T2.5 replaces it wholesale. Real agents cost money — no unbounded spawn even in M1.
- *Diff endpoint:* `git -C {worktree} diff <merge-base(base, HEAD)>` — committed + staged + unstaged tracked changes; untracked files excluded (documented limitation).
- *M1 gate:* `scripts/m1-gate.sh` (bash + curl + jq) run in CI on all 3 OSes (Git Bash on Windows): build vincent+fakeagent → temp dirs via env overrides → start daemon → register temp repo → create task → poll to done → assert branch/diff/transcript → stop daemon.

**Agent input-request decisions (grill session, 2026-08-07; spec §7.4):**

- *Trigger:* structured, machine-readable requests only — `question` (AskUserQuestion-style, options/multi-select/free text) and `permission` (restricted-mode prompt); nothing inferred from output text.
- *State:* new `awaiting_input`, **holds** its concurrency slot (live agent process idle mid-step); `answer` human action returns it to `running` in place; `cancel` valid from it.
- *Clocks:* step `timeout` pauses while waiting; new `input_timeout` (global default 24h in config `defaults`, overridable in workflow `defaults`/per step); expiry kills the process and fails the attempt (`input_timeout`) under normal retry/blocked policy.
- *API:* normalized `InputRequest` (kind, questions/options/multiSelect, adapter-native payload in `raw`) stored as task `pending_input`; durable `task.awaiting_input` event (kind + summary; full request via task GET); `POST /v1/tasks/{id}/answer` (409 outside `awaiting_input`). *(Amended by the PR F grill: no separate `task.awaiting_input` event type — the kind + summary ride `task.state_changed`'s payload, per PR D's one-event-per-transition rule; see the PR F block.)*
- *Opt-out:* `on_input: wait | deny` (workflow `defaults` + per step, default `wait`); `deny` = adapter auto-answers ("no user available — best judgment" / permission denied) so unattended workflows never stall.
- *Capability:* per-adapter `supports_input` — claude yes via bidirectional stream-json (`--input-format stream-json`, stdin kept open; control-message wire format is undocumented → pinned per detected CLI version, fixture-tested, degrades to `supports_input: false` if unverifiable); codex `exec` is strictly non-interactive → never enters `awaiting_input`. Unparseable control request = attempt fails `input_protocol_error`, never hangs.
- *Alerts:* TUI-level only (board pins needs-attention tasks + badge, header attention count, terminal bell on `task.awaiting_input`); OS desktop notifications stay post-v1.
- *Recovery/metrics:* crash while `awaiting_input` = `interrupted` (request discarded, fresh re-run may re-ask); request+answer transcripted as `vincent.*` lines; wait time in new `input_wait_ms` StepRun column, excluded from durations.
- *Phasing:* interface shape final in T1.7 (`InputRequest`/`InputResponse` types, `Respond()` on RunHandle, `RunSpec.OnInput`, `supports_input` in Detect — claude may report `false` until the engine lands); full engine as new T2.12 (incl. `pending_input_json`/`input_wait_ms` migration); TUI in T3.2/T3.4; fake agent grows an ask-question scenario.

**T1.3/T1.4 decisions (grill session, 2026-08-07):**

- *Start handshake:* `daemon start` first probes for a healthy daemon (already running = success), then spawns the detached child and polls `daemon.json` + `GET /v1/health` for ~10 s; on failure it prints the tail of `daemon.log` and exits non-zero. No pipe IPC.
- *Status truth:* try-acquire `daemon.lock` — acquirable means no daemon (a leftover `daemon.json` is reported as stale); held means alive, then `/v1/health` decides responsiveness. Exit codes: 0 healthy · 1 not running · 2 alive-but-unresponsive. Human-readable output; `--json` deferred to T4.2.
- *Idempotency:* desired-state semantics — `start` on a running daemon and `stop` with none running both print what happened and exit 0.
- *Stop flow:* `daemon stop` POSTs `/v1/daemon/stop` (202; response completes before shutdown begins), then waits for the lock to become acquirable (~20 s, longer than the daemon's own kill grace); `--force` falls back to killing the recorded PID.
- *Foreground = daemon:* `vincent daemon` is the real daemon in both modes — always takes the lock, writes token/`daemon.json`, always logs to the rotating file; foreground additionally mirrors logs to stderr. Log level rides a `slog.LevelVar` so `log_level` applies on hot-reload; a `listen` change is warned and the effective value kept.
- *Middleware order:* recover outermost → request log → auth → handler (panics always logged and enveloped as 500; unauthorized requests still logged). `/v1/health` is auth-exempt and logged at debug so poll loops don't spam the log.
- *Error vocabulary (initial):* `unauthorized`, `not_found`, `method_not_allowed`, `invalid_json`, `validation_failed`, `invalid_state`, `internal`; ServeMux fallback 404/405 wrapped so every error body is the §13.1 envelope (405 carries `Allow`).
- *`/v1/info` (initial):* version/commit/built, pid, `started_at`, uptime, effective listen address, `max_parallel_tasks`; agent availability joins in T1.7 (additive).
- *`/v1/config`:* effective config as snake_case JSON mirroring `config.yaml`; durations rendered as Go duration strings.
- *Token:* 32 bytes `crypto/rand` as hex, written atomically (temp+rename) 0600 at first start, reused unchanged on later starts.

**T1.5/T1.6 decisions (grill session, 2026-08-07):**

- *Repo shape:* strict toplevel only — registered path must equal `git rev-parse --show-toplevel`; bare repos and linked worktrees rejected; a subdirectory is rejected with an error naming the real toplevel (explicit beats magic).
- *Path identity:* absolute path required (client cwd ≠ daemon cwd); stored cleaned as-given; duplicates rejected at the handler by identity comparison (`os.SameFile` — sees through symlinks and Windows case aliases) against all existing projects, error names the existing project. No DB unique on `path` (a string constraint can't see aliases). Default-name collision on `name` UNIQUE → `validation_failed` suggesting an explicit name.
- *default_branch:* local branches only — every detection candidate and explicit value must resolve under `refs/heads/`; `origin/HEAD`'s short name counts only if a local branch of that name exists, else fall through (`main` → `master` → current HEAD branch → reject). Invariant: a stored `default_branch` always resolves locally at write time.
- *PATCH:* pointer-field JSON — absent = unchanged, explicit `null` clears (`default_workflow`, `max_parallel_tasks`); `null` on required fields is `validation_failed`. Path repoint re-runs full registration validation + duplicate check, and the effective `default_branch` (stored, or supplied in the same PATCH) must resolve in the new repo.
- *DELETE:* hard delete with explicit cascade in one tx (events → step_runs → tasks → project; FKs stay strict). Guard without `force`: 409 `invalid_state` with the non-archived count. `?force`: 409 if any task `running`; otherwise archives each non-archived task force-removing its worktree (force *is* the dirty confirmation), then cascades. Branches never deleted. Transcript-file cleanup joins in T1.8.
- *Dirty rule:* untracked files count — dirty = `git status --porcelain` non-empty, matching `git worktree remove`'s own refusal; force maps to `--force`. Remove is idempotent: worktree dir already gone → prune + succeed.
- *Create residue:* prune-then-fail — `git worktree prune` before `worktree add`; if the target dir still exists non-empty, typed `worktree_path_occupied` error. Nothing deleted without an explicit force.
- *Error surfacing:* one vocabulary — `worktree.Error.Reason` snake_case strings (`base_branch_missing`, `branch_exists`, `worktree_dirty`, `worktree_missing`, `worktree_path_occupied`, `project_path_missing`, `git_error`) double as future task `block_reason` values; HTTP layer reuses the existing code set (400 `validation_failed`, 409 `invalid_state`, 404 `not_found`) — no new codes.

## Phase 2 — Workflow engine (M2)

Milestone acceptance (§19 M2): a multi-step workflow (gate + command publish) runs unattended to the gate; an agent question round-trips awaiting_input → answer → resume; `kill -9` mid-step recovers correctly; caps honored under load.

**Phase 2 decisions (grill session, 2026-08-07):**

- *Delivery:* 7 PRs along dependency seams — **A** T2.1+T2.2 (registry + templates), **B** T2.3+T2.4 (FSM + step executors; the T1.8 interim admission loop stays alive), **C** T2.5+T2.6 (scheduler + human actions), **D** T2.7+T2.8 (SSE endpoints + crash recovery), **E** T2.9+T2.11 (codex + catalog/resolution), **F** T2.12 (input requests), **G** T2.10 (M2 gate). Durable event *writes* land early in B (the FSM is the only thing that changes state); only the SSE *endpoints* wait for D.
- *Engine shape:* actor per admitted task — one goroutine walking the snapshot steps, sole writer of that task's state. Grows `internal/taskrun` (existing daemon wiring) rather than a new package; `internal/workflow` (registry + templates) and `internal/scheduler` (admission) fill the reserved stubs.
- *Actor lifetime = one admission:* parking at `awaiting_gate`/`blocked`/`paused` persists state, releases the slot, and exits; approve/retry/skip/resume re-queue and a fresh actor resumes at `current_step`. `awaiting_input` is the sole exception — slot held, live process, actor stays (§7.4).
- *FSM:* pure `internal/taskstate` package (State type + transition table + `Can(state, action)`, exhaustively tested); `store` aliases the constants. Persistence is a compare-and-swap `TransitionTask(id, from, to, …)` with `WHERE state = ?`; zero rows → `ErrStateConflict` → HTTP 409 carrying the current state. No transition anywhere bypasses it.
- *Events:* `internal/events` broker. State change + `events` row in **one** SQLite transaction; publish to subscribers only after commit, row id = SSE `id:`. Live output never touches the table — per-task subscribers only; a slow live-output subscriber drops chunks, a slow state subscriber is disconnected (it resumes losslessly).
- *SSE:* `Last-Event-ID` → replay `id > cursor` from the table, then attach to the broker — subscription registered *before* the replay query so nothing slips through the seam (dedupe by id). `?types=` / `?project_id=` filtered server-side. 15 s `:heartbeat` comment. Per-task stream coalesces live output on a ~100 ms flush timer (§13.3's ~10 Hz); catch-up = fetch transcript, then follow.
- *Scheduler:* single goroutine — the only place `queued → running` happens, so caps can't race. Ordering + both caps in SQL (global count plus per-project counts; a project at its cap is skipped while the queue walk continues). Woken by any task state change, config reload, and project PATCH; 5 s safety tick. `awaiting_input` counts toward both caps.
- *Retry accounting:* `step_runs.attempt` is monotonic per (task, step_index) — history stays append-only and `{step_index}-{attempt}.jsonl` never collides. The retry *budget* counts consecutive failed attempts since the last human action (`retry` resets it, §6); `interrupted` runs are excluded entirely (§7.2). `.LastFailure` carries the previous *failed* attempt; the §8.4 failure block is appended for agent steps on any attempt > 1.
- *Templates:* `Option("missingkey=error")` — a typo'd field fails the step before spawn instead of rendering a hole into the prompt. Optional fields use `{{with}}`/`{{if}}`, as the §8.1 example already does.
- *Step rows for non-process steps:* a manual step writes a `running` step_run on entry (emitting `gate.waiting`) and terminalizes to `approved`/`rejected` on the human action, so gate wait time shows in the timeline; `skip` writes/terminalizes a `skipped` row. Every step index a task passes through has at least one row.
- *Shells:* POSIX `/bin/sh -c`; Windows probes `pwsh` at daemon start, falls back to `powershell`, logs the resolution once, re-probes on config reload. A step's `shell:` pin overrides; a pinned shell that isn't installed fails the step before spawn with reason `shell_unavailable` — never a silent fallback.
- *Action delivery:* engine keeps `map[taskID]*liveRun` (control channel + cancel func + RunHandle). Handlers validate via `taskstate`, persist with the CAS, then deliver; a missing live run is normal (task parked or already exited), not an error. `cancel` cancels the run context (procx tree-kill, 10 s grace, §6); `pause` sets a flag read at the next step boundary; `answer` forwards to `RunHandle.Respond`.
- *Crash recovery:* PID + `proc_started_at` journaled before spawn; on startup every `running` step_run → `interrupted`, and the process is tree-killed only when the PID exists **and** its start time matches (guards PID reuse). Owning task → `queued` at the same `current_step`, retry budget untouched; `awaiting_input` treated identically with `pending_input` cleared. Replaces T1.8's `SweepInterrupted`, which blocks instead of re-queuing.
- *`adhoc`:* becomes a **built-in registry entry** at lowest precedence (a real file named `adhoc` in either scope shadows it), so creation is one uniform path, `workflow` stays optional, and `scripts/m1-gate.sh` passes untouched. Keeps `max_retries: 0` so an ad-hoc run fails fast rather than doubling agent spend. **Spec addition** to §8.
- *Selection (§8.6):* pure resolver in `internal/agent`; catalog validation runs at workflow load (T2.1) *and* at `POST /v1/tasks` with the task override applied — known-invalid pair = 400 `validation_failed`, unknown value accepted with a warning. Resolution itself happens at step start and the resolved triple is written to the step_run.
- *edit+retry:* rewrites that step's `prompt`/`run` inside `tasks.workflow_snapshot` (the snapshot stays the single execution truth, §5.3), plus a migration adding `step_runs.prompt_override TEXT` and `step_runs.run_override TEXT` so the timeline can flag an edited attempt. **Spec addition** to §14. *(Amended by the PR C grill: two columns, not one — the wire body is `{ prompt_override?, run_override? }` and a command override stored under a column named `prompt_override` reads as a bug. The handler cannot write these directly; see the PR C block below.)*
- *Clocks:* real clock, shrunk durations in tests — timeouts are `context.WithTimeout` on real processes, so a fake clock buys mock fidelity, not determinism. Exception: T2.12's `input_wait_ms` accounting takes a `now func() time.Time` so the arithmetic is assertable without sleeping.
- *M2 gate:* new `scripts/m2-gate.sh` beside `m1-gate.sh` (which keeps guarding the spine) — scenario 1 multi-step workflow (agent → command → manual gate → command push to a local bare remote) with an input-request round-trip; scenario 2 hard-kill mid-step + recovery; scenario 3 cap stress. Windows hard-kill uses `taskkill /F /PID` (Git Bash `kill -9` can't reliably kill a native process); the script branches on `$OSTYPE`.

**PR C decisions (T2.5 + T2.6; grill session, 2026-08-07):**

- *Package seam:* `internal/scheduler` owns the admission goroutine, both caps, the ordering, **and** the only `queued → running` CAS in the codebase — the "caps can't race" guarantee above only holds if the CAS is inside the scheduler. It hands admitted tasks to `taskrun.Runner.Admit`, which spawns the actor and never blocks; `Runner.admit`/`loop`/`tickInterval` are deleted. `Admit` returns an error, and the scheduler applies `Interrupt` (`running → queued`) on failure, so a shutdown can never orphan a `running` row with no actor.
- *Wake plumbing:* one post-commit callback on the `Store`, fired by `TransitionTask` after the transaction commits, wired by the daemon to `scheduler.Wake`. Same shape the T2.7 broker needs ("publish only after commit"), so PR D rewires that single line to `broker.Publish` and the scheduler becomes a subscriber. Config reload and project PATCH wake explicitly.
- *Cap counting:* the slot-holding set from `taskstate.HoldsSlot`, never a hand-written `IN (…)`. `store`'s task-state constants become genuine aliases of `taskstate`'s — the two lists had already drifted (`store` was missing `awaiting_input` entirely), and a third copy must not become possible. `awaiting_input` exists for the scheduler in this PR even though its endpoint arrives in T2.12.
- *Admission query:* one query returns queued tasks in `priority DESC, created_at ASC`, each row carrying its project's slot count and cap; Go walks it maintaining live tallies, skipping capped projects while continuing. SQL cannot see its own in-flight admissions, so the incremental tally is Go by necessity — caps and ordering still live in SQL.
- *Startup sweep:* `SweepInterrupted` is hoisted out of `taskrun.Runner.Start` to an explicit daemon-startup call ahead of both components. Neither the scheduler nor the runner owns crash recovery, and T2.8 then replaces one call site instead of operating inside a package.
- *Action logic:* methods on `taskrun.Runner` (it already owns the live map, the step-row helpers and `Worktrees`); `internal/api` stays a transport shim — decode, call, map typed errors to 409/400/404.
- *Pause durability:* `tasks.pause_requested` is a persisted column. Engine transitions never clear it; every human action **except** `pause` clears it (each is a human saying "go"). A `queued` task carrying the flag is not admitted — the scheduler transitions it `queued → paused` and clears. Pause therefore survives a hard kill (which T2.8 re-queues) and a stale flag can never ambush a later admission.
- *Cancel:* handler CASes to `aborted`, then signals the live run's cancel func. The actor terminalizes its **own** step_run row as `interrupted` with `failure_reason: canceled` (new `ReasonCanceled`); when no actor is live — `queued`, `blocked`, `paused`, or `awaiting_gate` with its open manual row — the handler terminalizes it, same state and reason. §5.4 gains no `canceled` step state. Losing the race to admission returns 409 with the current state and **no** internal retry: silently converting "cancel a task that hasn't started" into "kill a live process" is a different act the human never saw.
- *Kill grace:* §6's "graceful term, then kill after 10 s" does not exist today — `procx` has only `Kill()` (SIGKILL / `TerminateJobObject`) and `steps.go` wires `runCtx.Done()` straight to it. PR C adds `Proc.Terminate()` — `SIGTERM` to the process group on POSIX; on Windows it falls through to `TerminateJobObject`, documented, since a Job has no graceful tree-term primitive and §6's `taskkill /T /F` is the same thing. Wired into the **cancel path only**: `Terminate` → 10 s → `Kill`. The step-timeout path keeps hard-killing (a step that blew its budget had its chance); T2.8 adopts the same helper for shutdown. One kill primitive, three callers, three PRs.
- *Retry budget reset:* `tasks.retry_cursor_at`, stamped by the `retry` handler and passed straight into the `since` parameter `store.CountStepAttempts` already takes.
- *edit+retry write path:* the handler holds the override text while the task is `blocked` — the next `step_run` does not exist yet, and the actor is sole writer of step-run rows. Bridge is `tasks.pending_override_json`: the handler rewrites `workflow_snapshot` **and** stashes `{"prompt":…,"run":…}`; the actor drains it onto the next attempt's two columns and clears it in the same write. Only the attempt the human actually edited is flagged, not every later auto-retry of that step — accurate, since the edit happened at a point in time even though the snapshot keeps it forever.
- *Gate/skip row mechanics:* from `awaiting_gate`, terminalize the open `running` row (`approved`/`rejected`/`skipped`) — no new row. From `blocked`, the `failed` row stays and `skip` appends a fresh `skipped` row at `attempt = Last+1`. `approve` and `skip` advance `current_step` in the **same CAS** as the state change (`TaskChange.CurrentStep`); `reject` holds the cursor and blocks with `block_reason: rejected`. Skipping the final step needs no special case: `current_step = len(steps)` → `queued` → the actor is admitted, the step loop body never executes, and it falls through to `complete`.
- *Archive:* 409 + `invalid_state` with `details.reason: worktree_dirty`, matching the project-delete precedent's status and code. `force` accepted in the body (§13.2) **and** as `?force` (symmetry with `DELETE /v1/projects/{id}`, and `hasForce` already exists). Worktree removal must succeed **before** the transition — unlike project delete the record survives here, and an `archived` task pointing at a live worktree is a lie; a removal failure is 409 and the task stays `done`/`aborted`.
- *Priority:* conditional `UPDATE … WHERE id = ? AND state IN ('queued','paused')`, zero rows → 409 with the current state, then a durable `task.priority_changed` event and an explicit scheduler wake. A reorder never touches `TransitionTask`, so without this it would fire neither — and a TUI watching a queue silently reorder under it is worse than one more event type.
- *Error envelope:* grows an `omitempty` `details` object — `{"error":{"code","message","details":{"state":"running"}}}` — so §13.1's "409 carrying the current state" is machine-readable instead of prose a client must regex. Additive: every existing response stays byte-identical. **Spec addition** to §13.1.
- *Task response:* gains `available_actions` (from `taskstate.HumanActionsFrom`, written and tested in T2.3 and called by nothing until now) and `pause_requested`. Both derived per response; the M3 TUI never reimplements the §6 table.
- *Migration 0003:* `tasks.pause_requested`, `tasks.retry_cursor_at`, `tasks.pending_override_json`, `step_runs.prompt_override`, `step_runs.run_override`. **Spec addition** to §14.
- *Scope:* PR C ships `cancel`, `pause`, `resume`, `retry`, `skip`, `approve`, `reject`, `archive` and `PATCH {priority}`. Not `/answer` (T2.12 owns the bidirectional stream, `pending_input` and the wait accounting) and not the SSE endpoints (T2.7). No stub routes — an unimplemented `/answer` gets the router's existing 404 rather than a 501 clients might learn to special-case.
- *Testing:* scheduler tests run against a **real store** (the caps and ordering are SQL — a fake store would test nothing) with a stub `Admitter` that blocks on channels: no processes, fully deterministic, proving the global cap, the per-project cap, capped-project-skipped-while-the-walk-continues, and `priority DESC, created_at ASC`. One `taskrun` fake-agent integration test proves the real seam wires up.

- *Board data comes from the server, not N+1 joins:* `GET /v1/tasks` grows a list-only `listTaskResponse` embedding `taskResponse` with `project_name` (LEFT JOIN projects), `step_total`, `step_name`, `cost_usd`, `input_tokens`, `output_tokens`. §15's board columns exist nowhere in today's DTO, and the alternative — `/v1/projects` + `/v1/tasks/{id}/steps` per row — is 22 calls per refresh for 20 rows *and* forces the TUI to parse `workflow_snapshot` YAML just to count steps. - *Cost is the sum of every attempt,* not the surviving one. A step that failed twice before succeeding rolls up all three `step_runs` rows — §17 says "aggregate cost across attempts", and the number a human opens the board for is what the task actually cost, which includes the attempts that went wrong. Payload is `{"current_step": N}` — §13.3's established "ids plus what changed, not the full object". Routing the advance through `TransitionTask` as a `running → running` self-transition was rejected: every valid-transition guard would have to special-case an edge the FSM otherwise treats as invalid.
