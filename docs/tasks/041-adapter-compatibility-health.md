# 041 — Adapter version compatibility and protocol health

**Status:** ✅ done (5/5)
**Opened:** 2026-08-28

Issue #148 asked for a tested-version range per adapter, a compatibility matrix
per vincent release, and five separately reported health facets: installed,
authenticated, protocol-compatible, permission-compatible and model-catalog.

Three of its seven acceptance criteria were already satisfied by shipped work,
one is a commit convention rather than code, and the per-release matrix is not
implementable for one of three adapters. What is built is the rest: two new
health facets reported everywhere the three existing ones are, and the one
security-sensitive capability gap moved from a step failure to a creation-time
refusal.

## What was already true

- **AC5 — binary updates invalidate cached probe results.**
  `internal/agent/catalog.go` keys every cache line on binary identity
  (resolved path + mtime), with `failureTTL` for probes that did not answer and
  `authTTL` for `logged_in` (spec §9.6, task 026). Upgrading a CLI invalidates
  the line by construction.
- **AC4 — unknown JSON fields stay forward compatible; malformed or oversized
  frames fail explicitly.** Unknown stream lines normalize to `EventUnknown`
  and are transcripted verbatim (tolerant parsing, phase 1 decision); every
  adapter bounds one line at `maxLineBytes` (16 MB), so an oversized frame
  latches `agent.FailureStreamError` and fails the attempt
  `agent_protocol_error` under the §7.2 budget (#139, spec §18).
- **AC1 — each adapter documents tested CLI versions** — half true. The
  versions were pinned in §9.2/§9.3/§9.7 prose and in fixture filenames, with
  no machine-readable form and no way for a user to ask "was the build I have
  ever verified?". That half is what this task builds.
- **AC7 — release notes state adapter compatibility changes.** Not code:
  `CHANGELOG.md` is generated by Release Please from Conventional Commits, so
  the requirement is a **convention** — spell adapter-compatibility commits
  `feat(agents):` / `fix(agents):` with the CLI version in the subject, and the
  release notes state it for free. Recorded here rather than built.

## Decisions

1. **2026-08-28 — The version verdict is advisory and blocks nothing,
   anywhere.** The issue's "tested minimum/maximum … by vincent release" is not
   implementable as written: §9.7 records that cursor's version is
   `2026.08.04-aaa8809`, calver plus a commit sha, with no gate to parse it
   into. Ranges are available for at most two adapters of three, and a gate
   that answers a different question depending on which adapter you ask is
   worse than no gate. The one existing version gate — claude's input family
   `[2.1.0, 3.0.0)`, PR F decision — gates **one capability** and degrades the
   invocation visibly rather than gating the adapter; that precedent plus
   §9.6's "probe failure degrades, never blocks" settles it. So: `tested` is an
   exact string match against a fixture-verified build, `untested` is the
   normal answer for a user on a current CLI and changes nothing, and
   `incompatible` is a build vincent knows breaks.
   *The alternative it beat:* a semver range per adapter, refusing or warning
   at admission. It would have had to invent an ordering for cursor's calver,
   and it would have turned "your CLI is newer than our fixtures" — the state
   of every healthy installation a month after a release — into a blocking
   condition.
2. **2026-08-28 — The `incompatible` list ships empty, and is exercised
   anyway.** vincent has observed no build that breaks its parsers, and
   inventing one would be a lie in a table users read. But a branch nothing has
   ever executed is a branch that is wrong on the day it is first needed, so
   each adapter exposes `SetIncompatibleVersions` — the seam
   `cursor.SetSandboxAvailable` already establishes — and tests drive the
   verdict through it.
   *The alternative it beat:* omitting the verdict until a bad build appears.
   Adding a third value to a published enum later is a wire change for every
   client; wiring it now costs one string in one table on the day it matters.
3. **2026-08-28 — `restricted` refuses at task creation; the engine reason
   stays as the backstop.** It is the only security-sensitive capability gap
   vincent has: every other missing capability degrades visibly, while running
   a step full-auto because restricting was unavailable inverts the choice the
   step made (§9.7). It is also the only one that can be judged with **no
   binary installed**, because the answer depends on adapter identity and
   `GOOS` — the same argument that makes `InputNever` decisive without a probe.
   The gate is an exact mirror of task 013's, down to the ordering of the three
   creation-time checks. `ReasonRestrictedUnsupported` keeps its place for a
   task whose daemon changed underneath it.
   Retries are deliberately **not** gated: the choice was creation-time
   enforcement, not creation-plus-admission, so `checkRetryInput` gains no
   sibling and the engine backstop catches what creation could not have known.
   *The alternative it beat:* leaving enforcement in the engine alone. A
   restricted cursor task on Windows then spends a worktree, an admission and a
   retry to learn a fact the daemon knew before the task existed.
4. **2026-08-28 — Two standing decisions are re-affirmed, and pinned by a
   test.** There is still **no pre-flight refusal on `logged_in: false`** (§9.5,
   task 003 decision 4): authentication stays visible, not blocking, and an
   unauthenticated run keeps failing `agent_unauthenticated` under the §7.2
   budget. And doctor's `Problems` set stays **closed** (task 005 decision 7):
   `untested`, `incompatible`, missing and logged-out adapters are rows in the
   agents group and never change `vincent doctor`'s exit code — an untested
   build is the normal state of a healthy machine, so admitting it to the
   unhealthy set would make the exit code fire almost everywhere.
   `TestAgentHealthIsNeverAProblem` asserts an adapter that is absent, logged
   out, untested and incompatible at once produces no problem, so neither
   decision can be weakened by accident.
5. **2026-08-28 — Five flat fields, not a nested `health` object.** Three of the
   five facets already had a flat field on four wire structs. Nesting one facet
   while four stay flat is worse than five flat; and model-catalog health is
   **not** duplicated at all, because §9.6 already defines `probe_error` as
   exactly "the option probe failed and you are reading the curated catalog".

## Verification

No **new** gate script, but an existing one had to move with the change:
`scripts/m5-gate.sh` scenario 4 is cursor + `restricted`, and it runs on the
Windows runner, where cursor genuinely cannot restrict. That leg used to post
the task and wait for a `restricted_unsupported` block; under decision 3 the
create call answers `400` instead, so the leg now asserts the refusal there —
the status, the `validation_failed` envelope, the step and agent named in the
message, and that no task was left behind. The POSIX legs are untouched, since
cursor can restrict there and the workflow simply runs.

This is the correction to a claim made when the task was first written — that
no gate could reach the incapable leg. It is true that no gate can *force* the
incapable answer on a capable host, which still needs the Go seam; it was not
true that no gate reaches it at all, because CI runs this one on Windows.
`docs/gates/m5-gate.md`'s manual leg remains where the real-Windows walkthrough
is recorded.

The Go tests cover: all three verdicts per adapter through `cmd/fakeagent`'s
`FAKEAGENT_VERSION` (now honored in every dialect); cursor's
`RestrictedSupport` on both platform legs, so the Windows answer is exercised
on every OS CI runs; `Catalogs.RestrictedPossible` spawning nothing and staying
permissive for an unknown adapter; `RestrictedMismatch`'s resolution rules;
`POST /v1/tasks` refusing and admitting, with the catalog problem reported
ahead of it; a live round-trip of every new field through the real handlers;
the closed `Problems` set; and a mutated `--help` fixture — a renamed `--model`,
a `--effort` with its enum removed — degrading to the curated catalog with its
static capability levels intact (issue #148 AC6).
